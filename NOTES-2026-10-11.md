# Release Notes & Field Findings — 2026-10-11

Live-verified findings relevant to `alirezax5/telegram-bot-php` from the
2026-10-11 test session (real traffic). English first, Persian summary after.

### 1. Managed Bots methods — live API contracts (proven)
- `request_managed_bot` → `request_id` MUST be **int**. String fails with
  `Bad Request: Field "request_id" must be a valid Number`. Keep the `int` type
  hint; document it.
- `getManagedBotToken(int $botId)` → returns a live child-bot token. On a human
  user id it returns `Bad Request: user is not a bot` (real response captured).
- Full live chain proven: `request_managed_bot` (keyboard button, request_id=1001)
  → user accepted → `managed_bot` update `{user: <human>, bot: <child>}` →
  `getManagedBotToken(bot.id)` → child `getMe` ✔ → child `sendMessage` delivered.
- Also reachable & clean-erroring (live): `answerChatJoinRequestQuery`,
  `answerGuestQuery` (`QUERY_ID_EMPTY` when empty), `getBusinessConnection`,
  `message_thread_id` in private chat (`message thread not found`, gated by
  `has_topics_enabled`).

### 2. Token transport — the only correct pattern (proven 8/8)
- The bot token travels ONLY in the URL path `/bot<token>/METHOD`.
  All header variants (Authorization: Bearer, X-Telegram-Bot-Api-Secret-Token,
  X-Bot-Token, Bot) with a wrong/absent path token → 401/404. Token in query
  string or JSON body → rejected. Do not add header-based token transport.
- Telegram→your-webhook carries `X-Telegram-Bot-Api-Secret-Token` = the secret
  YOU set in `setWebhook` (per-bot routing key), never the bot token.

### 3. secret_token multi-bot webhook routing (proven 7/7)
- Two bots, ONE webhook file, distinct `secret_token`s — identity always correct
  (message + callback_query legs, real traffic). The minimal router example is in
  `docs/en/guides/multi-bot.md` (and 6 more languages).
- `webhook.php` for multi-bot farms: validate `X-Telegram-Bot-Api-Secret-Token`
  with `hash_equals()`, route to that bot's token from the registry, 403 unknown.
