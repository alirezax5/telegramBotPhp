# telegramBotPhp

**English** · [فارسی](README.fa.md) · [中文](README.zh.md) · [Русский](README.ru.md) · [Français](README.fr.md) · [Português](README.pt.md) · [العربية](README.ar.md)

Lightweight PHP 8.1+ wrapper for the **Telegram Bot API** — zero runtime dependencies, full coverage of every current API method (186 bot methods) and every response/entity type (199 types).

Current release: **3.3.0** — see [CHANGELOG.md](CHANGELOG.md) (fixes a broken `getChatMember()` in 3.2.1, completes JSON serialization of nested parameters, strips nulls, fixes a cURL timeout leak; multi-bot flows verified live with two real bots).

## Requirements

- PHP >= 8.1
- cURL extension (`ext-curl`)
- JSON extension (`ext-json`)
- Composer

## Installation

```bash
composer require alirezax5/telegram-bot-php
```

## Quick Start

```php
require 'vendor/autoload.php';

use telegramBotApiPhp\Telegram;

// Long polling
$bot = new Telegram($_ENV['TELEGRAM_BOT_TOKEN']);

$updates = $bot->getUpdates(0, 100, 50);       // offset, limit, long-poll timeout (s)
foreach ($updates->result as $u) {
    $bot->setInputData($u);
    $chatId = $bot->chatId();
    $text   = $bot->text();

    if ($text === '/start') {
        $bot->sendMessage($chatId, 'Welcome!');
    }
}

// Webhook mode
$update = $bot->getInputData();                   // decodes php://input
if ($bot->isMessage()) {
    $bot->sendMessage($chatId, $bot->text());
}
```

## Multi-bot (two bots in one process)

```php
// Pattern 1 — independent instances (e.g. membership check via bot #2)
$bot2 = new Telegram($_ENV['BOT2_TOKEN']);
$member = $bot2->getChatMember('@mychannel', $userId);
$status = $member->result->status ?? 'left';      // member | administrator | creator | left | kicked

// Pattern 2 — token stack: bot #1 sends AS bot #2
$bot->switchToken($_ENV['BOT2_TOKEN']);
$bot->sendMessage($chatId, 'Sent as bot #2, from the bot #1 process');
$bot->restoreToken();

// Raw API access (full stdClass response)
$me = $bot->callRaw('getMe');
```

Full guide: [docs/guides/multi-bot.md](docs/guides/multi-bot.md).

## Mini App `initData` validation

A Mini App frontend gets a **signed** identity string from Telegram (`Telegram.WebApp.initData`). Verify it server-side before serving any user data — `telegramBotApiPhp\WebApp\InitData` implements the official HMAC-SHA256 scheme with constant-time comparison:

```php
use telegramBotApiPhp\WebApp\InitData;

$res = InitData::validate($_POST['initData'] ?? '', $botToken, ['max_age' => 3600]);
if (!$res['ok']) {
    http_response_code(401);
    echo json_encode(['ok' => false, 'error' => $res['error']]);   // bad_signature, auth_date_expired, ...
    exit;
}

$me        = $res['user'];        // ['id' => 555000111, 'first_name' => 'Ali', ...]
$startParam = $res['start_param']; // deep-link payload from ?startapp=...
```

Helpers: `valid()`, `user()`, and `build()` — a dev-only generator of correctly signed initData strings for testing endpoints before the frontend exists. Full guide: [docs/guides/mini-apps.md](docs/guides/mini-apps.md).

# Project Overview

**telegramBotPhp** is a lightweight, zero-dependency PHP 8.1+ wrapper for the Telegram Bot API.

## Purpose

Expose every Telegram Bot API method through an ergonomic, object-oriented PHP surface while keeping the runtime background minimal (PHP + cURL only — no external packages, no framework).

## Scope & Numbers

| Metric | Value |
|--------|-------|
| Bot API methods covered | **186** |
| Typed response/entity classes | **199** |
| PHP version | >= 8.1 |
| Runtime dependencies | **0** (uses `ext-curl`, `ext-json`) |
| Data style | PSR-4 autoload; `stdClass` decode + lazy typed wrappers |

## Extension of the API

The wrapper maps every endpoint to a **method** on `Telegram` (mixed in via domain *traits*), and every JSON response/entity to a **type** class under `src/Types/`.

## Design goals

1. **Completeness** — keep in sync with the official Bot API at `https://core.telegram.org/bots/api`.
2. **Ergonomics** — friendly getters (`text()`, `chatId()`, `mediaType()`) on top of raw objects.
3. **Reliability** — built-in HTTP retry with exponential backoff + `retry_after` handling, reusable cURL handle, long-poll timeout support.
4. **Zero lock-in** — no framework dependencies; usable from webhook or long-polling scripts.

See [folder-structure.md](folder-structure.md) for layout, [methods.md](methods.md) for the API surface, and [telegram-class.md](telegram-class.md) for the core class.

# Telegram core class

`telegramBotApiPhp\Telegram` is the single root object. Construct it with a token, call any API method, and read update data through convenience getters.

## Construction

```php
new Telegram(
    string $token,
    string $apiUrl = 'https://api.telegram.org',
    string $fileUrlTemplate = '{url}/file/bot{token}/{file_path}',
    int    $maxRetries = 3,
    int    $retryDelayMs = 500,
    int    $curlTimeout = 30
)
```

`$curlTimeout` is clamped to a minimum of 5. For long polling, `getUpdates(timeout:)` raises the cURL timeout to `timeout+5` so the socket isn't cut mid-poll.

## Update data

The constructor reads `php://input` (webhook) and stores it as `stdClass`. Switch data manually with `setInputData()`, read typed views via getters:

```php
$bot->message();            // ?Message
$bot->callbackQuery();      // ?CallbackQuery
$bot->editedMessage();      // ?Message
$bot->channelPost();        // ?Message
$bot->poll();               // ?Poll
$bot->chatMember();         // ?ChatMemberUpdated
// ... 20+ typed getters
$bot->checkUpdateExists('message');   // bool
$bot->getUpdateId();                  // int
```

Update getters are **cached** per update (instance cache cleared by `clearCache()` / `setInputData()`).

## Convenience getters (from `otherTrait`)

`text()`, `caption()`, `messageID()`, `fromId()`, `chatId()`, `firstName()`,
`lastName()`, `username()`, `languageCode()`, `isPremium()`, `chatType()`,
`msgType()`, `mediaType()`, `fileId()`, `mimeType()`, `fileSize()`, `isReply()`,
`replyToMessageId()`, `pathToUrl()`. These accept messages, edited messages, channel
posts, callback queries and business messages.

`msgType()` returns one of `PRIVATE|_TEXT|_MEDIA|_FORWARD`; `mediaType()` returns
`_PHOTO|_VIDEO|_AUDIO|_VOICE|...|_TEXT`.

## Multi-token switching

```php
$bot->switchToken('new-token');   // push
$bot->restoreToken();             // pop
$bot->clearTokenStack();
$bot->getTokenStackCount();
```

## HTTP / resilience (Telegram::bot)

`bot(method, data, isUpload)` is the low-level HTTP call. It:
- reuses a single cURL handle (`close()` / `__destruct` release it);
- retries up to `maxRetries` with exponential backoff for network errors, 5xx and 429;
- for HTTP 429, honours `parameters.retry_after` before retrying;
- returns a decoded `stdClass` on success, or `['ok'=>false,'error'=>...,'http_code'=>...,'attempts'=>...]` after exhausting retries.

`callRaw(method, data)` (public, from `method` trait) calls the API without wrapping the result in a typed object — useful for raw introspection.

## Direct low-level access

- `getFileUrl($filePath)` — build a download URL for a file from its path.
- `close()` — explicitly free the curl handle.

See [overview.md](overview.md) for the module map and [methods.md](methods.md) for the full method list.

# Type System

Every JSON response from the Bot API is decoded to `stdClass`, then wrapped in a `BaseType` subclass (lazy, magic `__get`).

## BaseType

`telegramBotApiPhp\Types\BaseType` (abstract) implements:

- `__get(string $name): mixed` — reads from the underlying array; returns `null` for missing keys.
- `__isset(string $name): bool`
- `getIterator(): \Traversable`
- `toArray(): array` — recursive: nested `BaseType` and arrays of `BaseType` are converted.
- `jsonSerialize(): array` — so `json_encode($type)` works.
- `static create(array|object $data): static` — factory used by all API methods.

Data arrives either as `stdClass` (constructor converts via `get_object_vars`) or an array, or another `BaseType`.

## returned* response wrappers

Each API method returns a **response** type such as:

| Response class | Result payload |
|----------------|----------------|
| `returned`               | `bool` (ok) |
| `returnedMessage`        | `Message` |
| `returnedUser`           | `User` |
| `returnedChat`           | `ChatFullInfo` |
| `returnedChatMember`     | `ChatMember` |
| `returnedFile`           | `File` |
| `returnedBotShortDescription` | `BotShortDescription` |
| `returnedArrayOfMessageId`, `returnedArrayOfChatMember`, ... | arrays of entities |
| `returnedInt`, `returnedString` | scalar |

They are thin typed wrappers: `ok`, `error_code`, `description` + `result`.

## Entity types

Message, User, Chat, ChatMember, StickerSet, Poll, GameHighScore, InlineQueryResult, InputMedia, InputRichMessage, etc. — 199 classes total, all extending `BaseType`.

## Why magic properties instead of typed public props?

- Zero maintenance: new API fields appear automatically (forward-compatible).
- The raw update/response objects stay the single source of truth.
- Trade-off: no IDE autocomplete for fields (see refactoring ideas in [methods.md](methods.md) / project roadmap).

To get raw data back: `$type->toArray()` or `json_encode($type)`.

# Webhook vs Long Polling

The SDK supports both delivery modes — you choose at the app level.

## Webhook (HTTPS required)

```php
$bot = new Telegram($token);
$update = $bot->getInputData();      // decodes php://input

if ($bot->isMessage()) {
    $bot->sendMessage($bot->chatId(), $bot->text());
}
```

- **Pros:** real-time, no polling load, no connection held open.
- **Cons:** requires a public HTTPS endpoint; callbacks logged by Telegram.

### Setup

```php
$bot->setWebhook('https://example.com/hook');
$bot->getWebhookInfo();
$bot->deleteWebhook();
```

> Note: the modern format allows `secret_token`, `max_connections`, `allowed_updates` via the `$options` array.

## Long polling (no public server needed)

```php
$bot = new Telegram($token);
$offset = 0;

while (true) {
    $updates = $bot->getUpdates($offset, 100, 50);   // offset, limit, longpoll timeout(s)
    foreach ($updates->result as $u) {
        $offset = max($offset, $u->update_id + 1);
        $bot->setInputData($u);
        // ...handle
    }
    usleep(200_000);   // 0.2s
}
```

- **Pros:** works behind NAT, no TLS needed, simple.
- **Cons:** holds a socket open; each poll is a network round-trip.

**Long-poll timeout note:** the SDK's default cURL timeout is 30s, but for `getUpdates` the timeout given to Telegram is used and the cURL timeout is raised to `timeout + 5` so the HTTP request isn't cut before Telegram replies.

### Lifetime / single-instance

Run exactly one polling process per bot. Two processes sharing `getUpdates` offset can silently consume updates from each other (see *silent bot* debugging). Use a process manager (systemd / supervisor) to keep it alive, not multiple concurrent processes.

## Choosing

- Public public-facing products (Telegram webhook) → **webhook.
- Local/dev behind NAT → **polling.
- Shared host that can't hold a process open → polling with a cron-triggered script is fine for low-frequency, but for a Telegram volume a persistent process is preferred.

# Retry & Resilience

The SDK ships a small, built-in HTTP reliability layer in `Telegram::bot()`.

## Retry policy

- **Attempts:** up to `maxRetries` retries (default **3**) after the first request.
- **Triggers to retry:** cURL/network error, `5xx` server error, and `429` (rate limit).
- **Backoff:** exponential — `retryDelayMs * 2^(attempt-1)` (default first delay 500ms → 1s → 2s).
- **429 honouring:** if the API response carries `parameters.retry_after`, the client sleeps that exact number of **seconds** before retrying (rather than the exponential guess). This avoids hammering the rate limiter.

## cURL behaviour

- A single cURL handle is created lazily and **reused** across calls (connection reuse under long polling). Free it with `close()` or on destruct.
- `CURLOPT_TIMEOUT` defaults to 30s (constructor `$curlTimeout`). For long-poll `getUpdates` with an explicit `timeout`, the socket timeout is raised to `timeout + 5` so a slow long-poll response isn't cut.
- SSL verification is ON (`CURLOPT_SSL_VERIFYPEER => true`).

## Failure return shape

When retries are exhausted, `bot()` returns a `stdClass`:

```php
(object)[
    'ok'       => false,
    'error'    => 'curl error message' ?: 'API Error after N attempts',
    'http_code'=> 200|429|5xx|0,
    'attempts' => N,
];
```

`callRaw()` returns this raw object; typed methods wrap the `result` field if present.

## In practice

```php
$bot = new Telegram($token, maxRetries: 5, retryDelayMs: 300, curlTimeout: 60);

$res = $bot->sendMessage($chatId, 'Hi');
if (!($res->ok ?? false)) {
    // handle API error via $res->error / $res->http_code
}
```

# Multi-bot guide

Running two or more bots inside one PHP process — checking channel membership with a
second bot's token, or letting bot #1 send messages as bot #2.

Two independent patterns are supported. Both were verified live with two real bots
(see [CHANGELOG.md](../../../CHANGELOG.md) for the evidence table).

---

## Pattern 1 — Independent instances

Each `Telegram` object owns its own token, cURL handle and update cache. Nothing is
shared between instances, so identity isolation is guaranteed by construction:

```php
use telegramBotApiPhp\Telegram;

$bot1 = new Telegram($_ENV['BOT1_TOKEN']);
$bot2 = new Telegram($_ENV['BOT2_TOKEN']);

// Scenario A (owner request): membership check executed by bot #2's token,
// from inside bot #1's process.
$member = $bot2->getChatMember('@mychannel', $userId);
if (($member->result->status ?? '') === 'member') {
    // user is in the channel — checked by bot #2
}

$bot1->sendMessage($chatId, 'این پاسخ از ربات ۱ است');
$bot2->sendMessage($chatId, 'این پیام از ربات ۲ است');
```

## Pattern 2 — Token stack on one instance

One `Telegram` instance can temporarily *become* another bot, send, and switch back.
The stack is LIFO: every `switchToken()` pushes the current token, `restoreToken()`
pops it.

```php
// Scenario B (owner request): bot #1 sends AS bot #2, inside bot #1's process.
$bot1->switchToken($_ENV['BOT2_TOKEN']);
$bot1->sendMessage($chatId, 'این پیام توسط نمونهٔ ربات ۱، اما با هویت ربات ۲ ارسال شد');
$bot1->restoreToken();

// The same instance is bot #1 again:
$bot1->sendMessage($chatId, 'و این یکی دوباره از ربات ۱ است');
```

Helpers: `getToken()`, `switchToken(string $token)`, `restoreToken()`,
`clearTokenStack()`, `getTokenStackCount()`.

> Prefer Pattern 1 when both bots are used constantly — the stack is designed for
> short, bracketed excursions. Pattern 2 keeps a single cURL handle (fewer sockets),
> Pattern 1 keeps identities permanently separated.

## Raw calls

`callRaw(string $method, array $data = [])` performs any Bot API method and returns
the **full decoded response** (`stdClass` with `ok`, `result`, `description`,
`parameters.retry_after`) — useful for methods added recently or diagnostics:

```php
$me    = $bot2->callRaw('getMe');          // $me->result->username
$probe = $bot2->callRaw('getChat', ['chat_id' => '@mychannel']);
```

## Framework integration (TelegramBase)

The [TelegramBase framework](https://github.com/alirezax5/telegramBase) wraps this
library with a `BotManager` registry:

- `BOT_EXTRA_BOTS="second:<token2>,third:<token3>"` (env) registers named bots at boot;
- plugins fetch them via `BotManager::getInstance()->get('second')`;
- `has('name')` must be checked first — `get()` of an unknown name silently falls back
  to the **main** bot, which would execute the call under the wrong identity;
- see `docs/en/multi-bot.md` in the framework repository.

## One webhook file, many bots (secret_token routing)

You can serve **any number of bots from ONE webhook file** — no extra folders, and
bot tokens never appear in URLs:

1. Give **every bot its own random secret** (`[A-Za-z0-9_-]`, 32+ chars).
2. Register the **same URL** for every bot, each with its own secret:
   `setWebhook?url=https://example.com/hook.php&secret_token=<this-bots-secret>`
3. Telegram echoes the secret back on every update in the header
   `X-Telegram-Bot-Api-Secret-Token`.
4. In `hook.php`, read the header, look the secret up in a registry
   (`secret → token`), then build the matching `Telegram` instance
   (Pattern 1) and process the update under that identity.

```php
// hook.php — the whole router in a few lines
$registry = [
    'secret-A...' => $_ENV['BOT1_TOKEN'],
    'secret-B...' => $_ENV['BOT2_TOKEN'],
];
$secret = $_SERVER['HTTP_X_TELEGRAM_BOT_API_SECRET_TOKEN'] ?? '';
if (!isset($registry[$secret])) { http_response_code(403); exit; }

$bot = new Telegram($registry[$secret]);           // that bot's identity
$update = json_decode(file_get_contents('php://input'), true);
// ... handle $update with $bot ...
```

The secret doubles as an authenticity check (requests without it are not from
Telegram — answer `403`). Verified live 2026-10-11: two real bots, one file,
7/7 deliveries with the correct identity every time.

Token storage options, short version: a fixed set of bots → `.env`; bots added
at runtime → DB table with the token column **encrypted at rest** (cache the
lookup); user-created children → Managed Bots, token fetched live from Telegram
with `getManagedBotToken($user_id)` and never written to disk.

## Pitfalls

- **`get()` fallback**: calling `get('unknown-name')` returns the main bot (with a
  warning log) instead of throwing — always guard with `has()`.
- **Token stack is per-instance**: switching tokens on `$bot1` does not affect `$bot2`.
- **Unbalanced restore**: if you `switchToken()` without a matching `restoreToken()`
  on an exception path, the instance keeps the borrowed identity. Use try/finally:
  ```php
  $bot1->switchToken($t2);
  try {
      $bot1->sendMessage($chatId, 'as bot #2');
  } finally {
      $bot1->restoreToken();
  }
  ```
- **File uploads inside JSON fields**: local paths for `stickers`, `media`, etc. are
  converted to `CURLFile` automatically (v3.3.0+) — but only before JSON encoding, so
  always pass PHP arrays (not pre-encoded JSON strings) for those parameters.

# Guide — Mini App `initData` validation

Telegram **Mini Apps** are web pages opened inside Telegram. The frontend receives `window.Telegram.WebApp.initData` — a query string **signed by Telegram** with your bot token. It is the only trustworthy proof of *which user* is using the app. This SDK ships a small validator that implements the official HMAC-SHA256 scheme:

```php
use telegramBotApiPhp\WebApp\InitData;
```

> **Never trust `initDataUnsafe`** — same fields, zero signature. Only the signed `initData` can be verified against the bot token. Mini App traffic does **not** go through the webhook: the user's browser calls your HTTPS domain directly, so the validator is pure PHP with no bot-API dependency.

## Validate in your endpoint

```php
use telegramBotApiPhp\WebApp\InitData;

// Accept form POST or a JSON body.
$raw = $_POST['initData'] ?? null;
if (!is_string($raw) || $raw === '') {
    $json = json_decode((string) file_get_contents('php://input'), true);
    $raw  = is_array($json) ? (string) ($json['initData'] ?? '') : '';
}

$res = InitData::validate((string) $raw, BOT_TOKEN, ['max_age' => 3600]);

if (!$res['ok']) {
    http_response_code(401);
    header('Content-Type: application/json; charset=utf-8');
    echo json_encode(['ok' => false, 'error' => $res['error']]);
    exit;
}

$user       = $res['user'];        // ['id' => 555000111, 'first_name' => 'Ali', ...]
$startParam = $res['start_param']; // deep-link payload from ?startapp=ref_7
$authDate   = $res['auth_date'];
```

## API

| Method | Signature | Returns |
|---|---|---|
| `validate()` | `validate(string $initData, string $botToken, array $options = [])` | Full result array |
| `valid()` | same args | `bool` |
| `user()` | same args | `?array` — the Mini App user or `null` |
| `build()` | `build(array $fields, string $botToken)` | A correctly **signed** initData string — tests, fixtures, local curl-ing |

**Success result:** `ok`, `user` (decoded array or `null`), `auth_date`, `start_param`, `fields` (all fields without the hash), `hash`.

**Failure result:** `ok: false` + `error`: `empty_init_data` · `bot_token_missing` · `malformed_init_data` · `hash_missing` · `bad_signature` · `auth_date_missing` · `auth_date_expired`.

**Options:** `max_age` — max accepted age of `auth_date` in seconds; default `86400`, `0` disables the check.

## Opening the Mini App

- Reply-keyboard button: `sendMessage($chatId, 'Shop', ['reply_markup' => ['keyboard' => [[['text' => 'Open Shop', 'web_app' => ['url' => 'https://your.domain/app']]]]]])`.
- Or set the bot's Menu Button in BotFather (`/setmenubutton`).
- Deep links: `https://t.me/yourbot?startapp=ref_7` → arrives as `start_param`.

## Local testing

```php
// fixtures/init.php
echo InitData::build(['user' => ['id' => 555000111, 'first_name' => 'Ali'], 'start_param' => 'ref_7'], BOT_TOKEN);
```

`curl --data-urlencode "initData@/tmp/init.txt" https://your.domain/app/api.php` — the endpoint sees a perfectly valid, freshly signed identity.

> `build()` is for development and tests only.

## Security checklist

- Validate server-side on **every** privileged request — the signature proves the user, not your business logic.
- Keep `max_age` tight (`3600` or less for sensitive operations).
- `hash_equals()` is used internally (constant-time); never compare hashes with `===`.
- Don't log `initData` or bot tokens.
- The additional `signature` field (Ed25519) is for validating **third-party** Mini Apps; for your own bot the HMAC `hash` check is the official and sufficient scheme.

## Algorithm reference

1. Parse `initData` as a query string; remove `hash`.
2. Data-check-string: remaining fields as `key=value`, sorted alphabetically by key, joined with `\n` (0x0A).
3. `secret_key = HMAC_SHA256(key="WebAppData", message=BOT_TOKEN)`
4. `computed   = HMAC_SHA256(key=secret_key, message=data_check_string)` — hex.
5. Valid iff `computed == hash` (constant-time) and `auth_date` within `max_age`.

Related: telegramBase users get the same validator with token auto-detection as `alirezax5\TelegramBase\App\MiniApp\InitData` — see the framework's `docs/en/mini-apps.md`.
